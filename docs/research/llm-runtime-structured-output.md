# LLM runtime and structured output for the MoM stages

Research for #34 (part of map #31). Researched on 2026-10-02. No models were run for this note because the GPU was busy. Everything below comes from documentation, source code, release notes and the local Ollama's metadata endpoints (`/api/version`, `/api/show` and `/api/ps`, none of which runs inference).

**Question.** `qwen3:8b` through Ollama sometimes fails the extract and summary stages with invalid, truncated or empty JSON. Which runtime and structured-output approach makes schema-valid output reliable on a GTX 1060 6 GB (Pascal, compute capability 6.1) with 16 GB RAM, local-only, with the model unloaded from the GPU between stages?

**Short answer.** Keep Ollama. On Linux and CUDA, Ollama 0.34.x already runs llama.cpp's `llama-server` and passes our schema to it as `json_schema`. Ollama's `format` therefore uses the same GBNF grammar engine that we would get by switching to llama.cpp. Changing the runtime would not fix the failures. The likely causes are in our own request settings and error handling: greedy decoding against Qwen's advice, unbounded schemas, tight `num_predict` and `num_ctx` budgets, an unchunked Summary input, and a retry that never fires. Fix those first. The other libraries (Outlines, xgrammar, lm-format-enforcer) do not fit this GPU (details below).

Legend: **[F]** = fact with a source. **[I]** = my inference, not verified by a run.

## 3. Likely causes of the current failures (tied to code)

When `think` is false, Ollama already constrains the output with a grammar (row 4). In that mode, *invalid* JSON can only appear if generation stops before the grammar completes. So almost every failure should be a budget or stopping problem, not a parsing problem. The candidates below are ordered by my estimate of likelihood.

1. **Greedy decoding causes repetition loops until the budget runs out.** **[F]** `temperature: float = 0.0` is the default (`config.py` lines 46 and 55) and is sent as `options.temperature` (`ollama.py` lines 102–106). This overrides the model's 0.6/0.95/20 defaults. **[F]** Qwen3's model card says: "**DO NOT use greedy decoding**, as it can lead to performance degradation and endless repetitions". It recommends Temperature 0.7, TopP 0.8, TopK 20 for non-thinking mode, and `presence_penalty` 0–2 "to reduce endless repetitions" (https://huggingface.co/Qwen/Qwen3-8B). The no-greedy warning is stated for thinking mode, and the non-thinking advice is a suggestion. **[F]** Ollama's own structured-outputs tips say to set temperature to 0 (https://ollama.com/blog/structured-outputs), so the two sources conflict. **[I]** With an unbounded schema (next item), a greedy loop inside a string or an `evidence` array keeps going until `num_predict`. The result is `done_reason == "length"` and the error "incomplete or empty response" (`ollama.py` lines 120–125), which reads as truncated JSON.
2. **The schemas have no length bounds.** **[F]** `schemas.py` has no `maxItems` on the section arrays or on `evidence`, and no `maxLength` on strings. **[F]** llama.cpp honours both keywords, and Ollama passes the schema through unchanged (row 2). **[I]** Adding bounds turns a runaway loop into a short, complete object.
3. **`num_predict` is small next to what the stage has to output.**
   - **[F]** Extract and translate use `StageConfig(8192, 4096)` (`config.py` lines 75 and 78). Chunks are sized to fill `(num_ctx − num_predict) × 2.5` characters of input (`application.py` line ~455).
   - **[I]** The English Transcript stage echoes every segment back, so its output is about the same size as its input. With about 4,000 tokens of input, 4,096 output tokens is tight.
   - **[F]** Summary uses `StageConfig(4096, 512)` (`config.py` line 81).
   - **[I]** 512 tokens is enough for a paragraph only if `think` stays false. If someone sets `think = true` for the Summary stage, the thinking tokens count against `num_predict`, content comes back empty, and the result is an "empty response".
4. **The Summary input is not chunked.** **[F]** `application.py` line 318 serialises *all* reconciled facts into one Summary call. `ollama.py` lines 85–89 then raise `ValueError` when `len/2.5 + 512 > 4096`, which happens above roughly 8,900 characters of facts. **[I]** This fails deterministically on longer meetings rather than intermittently, but the user may see it as "the MoM step fails".
5. **The retry is dead code for the real failure modes.** **[F]** `_json_call` (`application.py` lines 439–448) retries only when `json.loads` or the validator fails on the returned text. But `chat()` raises `RuntimeError` itself for invalid JSON (`ollama.py` line 130), for `done_reason == "length"` or empty text (lines 120–125), and for context exhaustion (line 119). Those exceptions are not caught, so **the "one retry" never runs**. **[I]** At temperature 0, a retry would produce the same output anyway. A retry only helps with sampling, or with a changed budget or prompt.
6. **The token estimate may be optimistic for Arabic.** **[F]** `ollama.py` line 85 assumes 2.5 characters per token. The direct pipeline sends Egyptian Arabic. **[I]** If Qwen3 tokenises this Arabic at fewer than 2.5 characters per token, `prompt + output` can reach `num_ctx`. That trips the guard on lines 115–119 ("exhausted num_ctx").
7. **Thinking with `format` on 0.34.2.** **[F]** This path is lossy (row 5). **[I]** It is relevant only if a stage config sets `think = true`. The defaults do not.
8. **Timeouts on the CPU/GPU split.** **[F]** The model is partly on CPU (row 6). Extract and translate allow 600 s per call (`config.py` lines 75 and 78). **[I]** A 4,096-token runaway at single-digit tokens per second can exceed 600 s, which shows up as `TimeoutError`. This is consistent with "intermittent" failures and interacts with cause 1.

Also note **[F]**: the prompts (`prompts.py`) do not describe the schema fields. The model sees field names only through the grammar mask. **[I]** Describing the fields in the prompt usually reduces degenerate fills, but this is a quality lever, not a validity one.

## 4. Recommendation

1. **Runtime: stay on Ollama** and upgrade to **≥ 0.34.4** (0.35.1 is current). The upgrade gets the single-pass thinking-plus-schema fix, so `think = true` becomes usable for extraction if it is ever wanted. It also keeps the existing unload logic (`keep_alive: 0` plus `/api/ps`) and digest Provenance. Switching to `llama-server` directly would use the same grammar engine (row 2) and buys only finer control (`--reasoning-budget`, `--n-cpu-moe`). Revisit it only if #33 picks a MoE model that needs `--n-cpu-moe`-style offload Ollama does not expose.
2. **Structured output: keep the JSON schema in `format`**, and turn the fixes below into ready-for-agent tasks. These are not done here, by design.
   - Bound the schemas: add `maxItems` to each section array and to `evidence`, and `maxLength` to strings.
   - Stop greedy decoding for Qwen3. Use the model-card non-thinking settings (temperature 0.7, top_p 0.8, top_k 20), or keep a low temperature and add `presence_penalty`. Measure the effect with `ea accuracy`.
   - Make `chat()`'s length, empty and invalid-JSON errors retryable inside `_json_call`. When a retry happens, also either halve the chunk size or raise `num_predict`.
   - Chunk or condense the Summary input, and raise Summary `num_predict`.
   - Log `done_reason`, `eval_count` and `prompt_eval_count` with each failure, so the next failure says which cause it was.
3. **Do not adopt** Outlines, xgrammar or lm-format-enforcer. The engines they would sit on either do not support Pascal (vLLM needs compute capability ≥ 7.5) or already provide the same constraint through llama.cpp.

## 5. Open questions / not verified

- **Which failure messages actually occurred.** No run log or recorded error was found in the issues or the repo. This note does not know whether the failures were "incomplete or empty", "invalid JSON", "exhausted num_ctx", `ValueError` (budget) or `TimeoutError`. The first diagnostic task should capture `done_reason` and the token counts.
- How many characters per token Qwen3 actually produces for Egyptian Arabic and for the English Transcript JSON. This would validate or replace the 2.5 heuristic.
- Whether non-greedy sampling or `presence_penalty` changes MoM critical-fact accuracy. It needs an `ea accuracy` run, which is a separate task ticket.
- How Ollama ≥0.34.4 actually behaves with `qwen3:8b` + `think: true` + `format`. That needs a run, and the GPU was busy.
- Whether llama-server's grammar sampling adds noticeable per-token overhead with partial CPU offload on the i7-7700HQ. Not measured.
- SGLang and TensorRT-LLM support for Pascal was not checked. vLLM's limit (≥ 7.5) is the only one verified.
